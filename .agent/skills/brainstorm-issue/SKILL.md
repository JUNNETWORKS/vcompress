# 壁打ち → Issue 化 スキル

`$ARGUMENTS` の要望について、対話で要件を詰めてから GitHub Issue を起票する。

## 進め方

### Step 1: 現状把握（壁打ち開始前）

コードを読んで現状を把握してから論点を出す。前提を勘違いしたまま壁打ちを進めると後半で全部やり直しになる。

- ディレクトリ構造、関連ファイルの Read
- 把握内容を「現状の構造」として 3〜5 項目で要約しユーザーに提示
- 「ここまで合っていますか？」と確認はせず、続けて論点提示に入って良い（ユーザーが違和感を持てば指摘してくる）

### Step 2: 論点の提示（壁打ちループ）

**1 ラウンドで最大 4 論点まで** に絞り、影響度（実装方向性に与える差）が大きい順に並べる。

各論点には必ず以下をセットで含める：

- 選択肢を 2〜4 つ、ラベル `(a) (b) (c)` で番号付け
- 各選択肢の **トレードオフ**（メリット・デメリット・実装コスト）を 1〜2 行
- Codex 自身の **推し案 + 理由**

ユーザーは「論点 X: a」のように番号で答えやすくなる。

ラウンド分割の目安：

- **第 1 ラウンド**: 「機能の意味づけ / 実行モデル / UX」など、最も大きな方向性軸 3 つ
- **第 2 ラウンド**: 第 1 ラウンドの選択を踏まえた次の論点（永続化・失敗時の挙動・UI・API 設計 など）
- **最終ラウンド**: 「既存機能との関係 / 出力先 / キャンセル等の細部」を 3〜4 問でまとめて

### Step 3: 詰めすぎを避ける

- すべてを聞き切る必要はない。Codex の推し案で十分なものは「実装時に判断」として **Open Questions** に回す
- 1 ラウンドで 4 論点を超えそうなら次ラウンドに分ける
- ユーザーから「もう書いて」と言われたら即 Issue 化に移る

### Step 4: Issue 作成

詰め終わったら以下を確認してから作成：

1. `git remote -v` でリポジトリと host を確認
2. `gh auth status --hostname <host>` で認証確認（NG なら作成前にユーザーに知らせる）
3. 出力先がユーザーから明示されていなければ「GitHub Issue / ExecPlan(`docs/plans/*.md`) / 両方」のどれか確認

### Issue 本文の構造（必須セクション）

```
## 概要
1〜2 段落で「何をどう変えるか」を端的に。

## 背景 / モチベーション
なぜ必要か。現状の課題を箇条書き。

## スコープ
### 含める
- 箇条書き
### 含めない
- 箇条書き（明示的な除外をここで宣言する。スコープ膨張の防波堤）

## 仕様
壁打ちで決めた内容を項目別（入力 / 実行 / 永続化 / UI / API / DB スキーマ等）に整理。
表が有効な場面では Markdown 表を使う。

## 影響範囲
変更するファイル・ディレクトリを箇条書き。

## マイルストーン（案）
1. ExecPlan 作成（プロジェクトに ExecPlan 規約があれば最初のステップに含める）
2. ...

## Open Questions
詰め切らなかった点・実装時に判断する点を箇条書きで残す。
```

### Issue 投入コマンド

`gh issue create` は HEREDOC で本文を渡す（バッククォートやドルが含まれていても安全）：

```bash
gh issue create --repo <owner>/<repo> --title "..." --body "$(cat <<'EOF'
...
EOF
)"
```

作成したら Issue URL をユーザーに返す。

### Step 5: 決定事項のサマリー

Issue URL に続けて、壁打ちで決めた論点と回答を **表形式** でユーザーに提示する。後から決定の経緯を辿れるように。

| 論点 | 決定事項 |
|---|---|
| ... | ... |

## やってはいけないこと

- 論点の選択肢を 5 つ以上並べる（決められなくなる）
- 選択肢にトレードオフや推し案を添えない（ユーザーが判断材料を持てない）
- 1 ラウンドで 5 論点以上聞く（疲弊する）
- 関連コードを読まずに壁打ちを始める（前提がズレる）
- 決定前に Issue を書き始める
- ユーザーの選択を勝手に上書きする / 黙って変更する
- Issue 本文に「含めない」セクションを書かない（スコープ膨張の原因）
- プロジェクトに ExecPlan 規約がある場合に Issue だけで済ませる（着手時の ExecPlan 作成をマイルストーンに含める）
